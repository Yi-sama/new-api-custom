# 2026-09-23 New API First-Token Investigation

## Symptom

The US deployment of new-api appeared to have unusually slow first-token latency.

## Scope

- Target: US server `156.238.252.115`, `root`, `api.yisama.asia`
- Inspection window: 2026-09-23
- Read-only investigation; no service, container, proxy, database, or configuration changes

## Evidence

- Host identity matched the selected US server. Host resources were healthy: 7.8 GiB RAM, about 6.5 GiB available, low load, 2 GiB swap nearly unused, and no OOM evidence.
- `new-api` was healthy, running without a restart, with low memory use and no sustained CPU pressure.
- `/api/status` timings were about 2-5 ms through the published container port, 10-14 ms through direct local Nginx TLS, and 60-106 ms from the US host through Cloudflare. A request from the current network was about 0.8-1.0 s through Cloudflare.
- The active container image is `calciumion/new-api:v1.0.0-rc.28`, but the executable is overridden by a read-only host bind mount under `/opt/proxy/newapi/releases/20260922-1655-local3000-73BC11F5/new-api`.
- The Nginx API location has `proxy_buffering off`, `proxy_cache off`, and 300-second proxy timeouts. The proxy path is not the source of multi-second first-token waits.
- The application records FRT in `other.frt`; the stream scanner sets the first response time as soon as it receives the first non-empty upstream `data:` event, before response conversion and downstream writing.
- 1,496 non-negative FRT samples were found in the last 24 hours: median 10.8 s, P90 39.5 s, P95 56.7 s, maximum 124.4 s. Prompt sizes at or above 128k had a 17.1 s median and 56.2 s P90; `xhigh` reasoning had a 21.3 s median and 64.7 s P90. These are correlations, not proof of a single provider-side mechanism.
- Channel 32 produced 233 observed 502 failures in the checked two-hour period. Failures completed in about 5.2-5.6 s and were logged as `Upstream service temporarily unavailable`; this is distinct from the slow successful streams.

## Conclusion

The US host, new-api request entry, Nginx, Cloudflare path, and local resource state are not consistent with the primary cause of slow first tokens. The dominant delay is before the first upstream SSE event, so it is upstream model/provider processing, channel proxy/provider path, request context size, reasoning mode, or upstream queueing. Large contexts and `xhigh` requests are the strongest observed correlates. Channel 32 currently also has an upstream availability problem.

## Follow-up

- Compare the same redacted request through channel 32/34 and directly to the owning upstream, recording DNS/connect/TLS/header/first-byte timings.
- Check channel 32's upstream endpoint and channel-level proxy health without exposing keys.
- Consider reducing prompt history and reasoning effort for latency-sensitive traffic; this is an operational mitigation, not a confirmed root-cause fix.

## Tool Errors

- One remote timing command used an invalid SSH option and did not run.
- Two remote aggregation attempts had PowerShell/SSH quoting issues; they were read-only, had no file impact, and were replaced with corrected probes. The corrected FRT statistics and raw request traces were verified.
- Full frontend `tsgo -b` runs intermittently failed with `runtime: cannot allocate memory`, including one later run at `GOMAXPROCS=2`. Re-running alone with `GOMAXPROCS=1` completed successfully, so the failure was tool parallelism/resource pressure rather than a remaining TypeScript diagnostic.
- One Windows `rg` search used a shell-style `model/*_test.go` path and reported an invalid path syntax error. It was read-only and was replaced with `rg ... model -g '*_test.go'`.
- One yielded Vitest session was reclaimed before its output could be read. The same focused test command was rerun and all three tests passed.
- The normal stop script found no PID file even though port 3000 was listening. `Get-Process` verified the listener was this repository's `bin/new-api-local-b-c.exe`; that exact process was stopped and the port was checked before replacement.
- WMI/CIM command-line inspection was unavailable with `Win32_Process` reporting an invalid class. Process identity and executable path were still verified through `Get-Process`.
- One runtime-check script used `$home`, which conflicts with PowerShell's read-only `$HOME`, and one response-body helper lost its stdout. Both were read-only; corrected checks confirmed `/api/status` 200, the expected process path, the new image chunk 200, and empty stderr.
